## 任务上下文
- 当用户在与代理（您）进行工作会话时，达到了 LLM 上下文限制
- 将以下对话浓缩为结构化摘要，仅移除最冗长的部分
- 包含用户请求、您的回复、所有技术内容，以及尽可能多的原始上下文
- 这将用于让用户继续工作会话
- 摘要将在下一次交换时由代理（您）读取，以便允许会话继续

**对话历史：**
{{ messages }}

在 `<analysis>` 标签中包裹推理过程：
- 按时间顺序审查对话：用户目标、您的方法、关键决策、文件、错误、修复
- 保持简洁 - 分析将被丢弃，因此它是一个包含内容的清单，而不是详细说明的地方

在结束的 `</analysis>` 标签之后，准确输出一个 ```json 代码块，且仅输出此内容，匹配以下模式：

```json
{
  "user_intent": ["每个用户目标和请求，最重要的在前"],
  "technical_concepts": ["所有讨论的工具、方法和概念"],
  "files": [
    {
      "path": "被查看或编辑的文件路径",
      "summary": "对该文件做了什么以及原因",
      "key_code": "该文件的重要代码、签名或差异（如果没有则省略）"
    }
  ],
  "errors_and_fixes": ["遇到的错误、其解决方案和用户驱动的更改"],
  "problem_solving": ["已解决或进行中的问题，以及关键决策：选择了什么、拒绝了什么以及原因"],
  "user_messages": ["所有用户消息，截断长工具调用参数或结果"],
  "pending_tasks": ["所有未解决的用户请求，最重要的在前"],
  "current_work": "摘要请求时的活跃工作：文件名、代码、与最新指示的对齐",
  "next_step": "仅当它直接延续用户指示时包含，否则省略"
}
```

JSON 规则：
- `<analysis>` 代码块是一个被丢弃的草稿：仅 JSON 存活，因此它必须自包含，并重复分析中与继续工作相关的每个细节
- 按重要性排序每个列表，从最重要到最不重要的
- 每个列表条目必须是纯字符串，而不是嵌套对象 - 例外是 `files`，其条目是如上所示的对象
- 在 `errors_and_fixes` 中逐字引用错误消息、panic 文本和失败的测试输出 - 包括数字、标识符和路径在内的精确字符串，而不是意译
- 此摘要仅由您阅读，因此可以比您向人类展示的正常摘要长得多：将您的整个长度预算用于 JSON 字段，并自由引用 - 完整输出块、完整代码片段、准确的用户措辞
- 不要排除任何可能与继续与您一起工作的会话有关的信息
- 对于字段，宁可省略也不要编造内容
- 除非用户确认，否则不要提出新想法
